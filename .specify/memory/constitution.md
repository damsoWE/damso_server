# 담소(DAMSO) 백엔드 Constitution

## Core Principles

### I. 연락처 미수집

- 전화번호·주소 등 연락처를 수집하거나 저장하지 MUST NOT 한다.
- `users` 테이블을 포함한 어떤 테이블에도 연락처 컬럼을 두지 MUST NOT 한다.
- 학부모와 교사 어느 쪽도 API를 통해 상대의 연락처를 알 수 없어야 MUST 한다.
- 이메일은 연락처로 보지 않는다. 가입 인증·로그인 식별용 최소 인증 수단으로만 쓰며, 다른 사용자에게 노출하지 MUST NOT 한다.

근거: 교사 개인번호 노출 문제를 기능이 아닌 데이터 부재로 해결한다. 없는 데이터는 유출되지 않는다.

### II. 가명화 게이트웨이 경유

- 외부 LLM으로 나가는 모든 텍스트는 가명화 게이트웨이를 거쳐야 MUST 한다. 우회 호출 경로를 두지 MUST NOT 한다.
- 가명화 대상: 학생명·보호자명·교사명·학교명·학급, 그리고 패턴 탐지로 찾은 전화번호·주소.
- 복원표는 요청 처리 중 메모리에만 존재해야 MUST 하며, DB·캐시·파일 저장과 로그 출력을 MUST NOT 한다.

근거: 아동·청소년 개인정보가 외부 API 경계를 넘지 않음을 구조로 보장한다.

### III. 원문 보존과 열람 감사 (append-only)

- 문의 원문은 암호화해 저장해야 MUST 한다.
- 원문·정제본·처리 이력에 대한 수정·삭제 API를 제공하지 MUST NOT 한다.
- 원문 열람은 열람자·대상·시각을 감사 로그에 기록해야 MUST 한다. 감사 로그 역시 append-only다.

근거: "검열" 오해를 차단하고, 교권보호위원회 등에 제출할 기록의 무결성을 확보한다.

### IV. 긴급 우선 — 긴급 fail-open, 일반 fail-closed

- 학생 안전·학대·자해 관련 긴급 판정은 LLM 호출 이전에 규칙 기반으로 수행해야 MUST 한다.
- 긴급 판정은 보수적으로 한다. 의심되면 정제를 건너뛰고 교사에게 즉시 전달·알림한다(fail-open).
- 긴급 경로는 LLM·외부 API 장애와 무관하게 동작해야 MUST 한다.
- 일반 정제가 실패하거나 출력 검증에 실패하면 1회 재시도 후 "원문 확인 필요" 상태로 전이하고 교사에게 알린다(fail-closed). 검증되지 않은 정제 결과를 교사에게 보여주지 MUST NOT 한다.

근거: 외부 장애가 안전 사안의 전달을 막지 못하게 하고, 잘못된 정제가 사실처럼 전달되는 것을 막는다.

### V. 제안만 한다 — 자동 발송 없음

- 답변 점검 결과는 제안으로만 제공해야 MUST 한다.
- 교사의 명시적 전송 행위 없이 학부모에게 메시지를 발송하는 경로를 두지 MUST NOT 한다.
- 시스템이 교사 답변을 대신 작성하거나 수정해 저장하지 MUST NOT 한다.

근거: AI 오작동이 곧 실제 발신이 되는 사태를 차단한다. 판단과 책임은 교사에게 있다.

### VI. 민감정보 비노출 (로그·에러)

- 문의·답변 본문과 정제 결과를 애플리케이션 로그에 출력하지 MUST NOT 한다. 로그에는 식별자(UUID)와 상태만 남긴다.
- 에러 응답에 스택트레이스·예외 클래스명·내부 경로·SQL을 노출하지 MUST NOT 한다. 전역 예외 처리로 에러 코드와 일반 메시지만 반환한다.

근거: 로그와 에러 응답은 가장 흔한 유출 경로다.

### VII. UUID 식별자와 건별 소유권 검증

- 외부에 노출되는 모든 식별자는 UUID여야 MUST 한다. 순번 ID를 API에 노출하지 MUST NOT 한다.
- 모든 리소스 접근은 서비스 계층에서 건별로 소유권·권한을 검증해야 MUST 한다.
  - 학부모: 본인이 작성한 문의와 그 답변만
  - 교사: 담당 학급의 문의만
  - 학교 관리자(도입 시): 메타데이터만, 내용 열람 권한 없음
- 요청 본문·파라미터로 받은 역할·사용자 ID를 권한 판단에 사용하지 MUST NOT 한다. 인증 주체와 DB 기준으로만 판단한다.

근거: 수평 권한상승(타인 문의 조회)을 단일 지점에서 차단한다.

### VIII. 안전한 기본값

- 시크릿(DB 비밀번호, 암호화 키, JWT 서명 키, LLM API 키)은 환경변수로만 주입해야 MUST 한다. 코드·설정 파일에 하드코딩하지 MUST NOT 한다.
- 필수 시크릿이 없거나 형식(키 길이 등)이 맞지 않으면 애플리케이션은 기동을 거부해야 MUST 한다.
- 기본 계정·기본 비밀번호를 제공하지 MUST NOT 한다.

근거: 공개 저장소를 그대로 배포했을 때 설치 실수가 유출로 이어지는 경로를 막는다.

## 백엔드 보안 요건

- **LLM 출력 검증**: LLM 호출은 출력 스키마를 강제(Structured Outputs strict)하고, 서버에서 스키마·허용값을 재검증해야 MUST 한다. 위반 출력은 폐기한다.
- **LLM 출력 격리**: LLM 출력을 쿼리·파일 경로·URL·권한 판단 등 실행 경로에 사용하지 MUST NOT 한다. 시스템 지시와 사용자 입력은 역할을 분리해 전달한다.
- **SQL**: 파라미터 바인딩만 사용해야 MUST 한다. 문자열 연결로 쿼리를 만들지 MUST NOT 한다.
- **토큰**: Access Token과 Refresh Token을 분리한다. Refresh Token은 사용 시 1회 회전하며, 이미 사용된 토큰의 재사용이 탐지되면 해당 토큰 계열 전체를 폐기해야 MUST 한다. JWT 서명 알고리즘을 고정하고 `alg=none`을 거부한다.
- **동시성**: 상태를 가진 엔티티의 상태 전이는 낙관적 락(`@Version`)으로 검증해야 MUST 한다. 허용되지 않은 전이는 거부한다.
- **암호화**: 문의·답변 본문은 AES-256 기반 컬럼 암호화를 적용한다. 토큰·키·IV 생성에는 `SecureRandom`을 사용한다.
- **보안약점 관리**: 행정안전부 「소프트웨어 개발보안 가이드」(2021) 구현단계 49개 항목을 `docs/security-checklist.md`에서 조치/미조치/해당없음 3단으로 관리한다.

## 개발 흐름과 품질 게이트

- **기획서 취급**: `docs/아기하마_개발기획서.pdf`는 참고 자료이며 개발 중 바뀔 수 있다. 기획서와 달라지는 결정은 `docs/decisions.md`에 `날짜 | 원래 → 변경 | 이유`로 기록해야 MUST 한다. 이 constitution의 원칙은 기획서 변경으로 바뀌지 않는다.
- **명세 주도 개발**: 기능은 spec-kit 흐름(specify → clarify → plan → tasks → implement)을 따른다. spec에는 무엇/왜만 쓰고 기술 스택은 plan에서 정한다.
- **Contract-first**: API 변경은 `docs/api/openapi.yaml`을 먼저 수정 → 프론트 공지 → 코드 수정 순서를 따른다. 명세가 바뀌면 `api-vX.Y` 태그를 찍는다.
- **Contracts 리뷰**: plan 단계에서 생성된 contracts는 사람이 소유권 검증, 에러 응답 형식, UUID 노출 여부를 리뷰한 뒤 tasks로 넘어가야 MUST 한다.
- **머지 게이트**: AI 생성 코드를 포함한 모든 변경은 PR 리뷰와 CI 보안 검증(Gitleaks 등)을 통과해야 머지한다.
- **문서 언어**: spec·plan·tasks 등 프로젝트 문서는 한국어로 작성한다.

## Governance

- 이 constitution은 기획서, 개별 spec, 에이전트 지침(`CLAUDE.md`, `AGENTS.md`)보다 우선한다. 충돌 시 constitution을 따른다.
- **개정 절차**: 개정은 PR로만 한다. PR에는 변경 이유와 영향받는 spec·코드 목록을 적고, 백엔드 담당 2인 모두의 승인을 받는다.
- **원칙 I~VIII 변경**: 프론트엔드 레포(`damsoWE/damso_app`) constitution에도 같은 원칙이 있으므로 두 레포를 같은 시점에 함께 개정해야 MUST 한다.
- **버전 정책**: 원칙 삭제·재정의는 MAJOR, 원칙·섹션 추가나 실질적 확장은 MINOR, 문구 정리는 PATCH로 올린다.
- **준수 점검**: `/speckit-plan`의 Constitution Check와 PR 리뷰에서 원칙 준수를 확인한다. 위반이 불가피하면 plan의 Complexity Tracking에 사유를 적고 리뷰어 승인을 받는다.
