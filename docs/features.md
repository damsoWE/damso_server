## F1. 인증·회원가입·학급 연결

**왜**: 학부모는 자기 자녀의 담임에게만, 교사는 담당 학급에만 닿아야 한다. 이후 모든 기능의 권한 판단이 이 연결에서 나온다.

**초대 코드 기반 가입·매칭 흐름** [팀 결정 2026-10-15]

```
슈퍼 관리자 (코드 발행 전담, 민원 열람 권한 없음)
 ├─ 교사 초대 코드 발행 (학급 지정) ──────────→ 교사가 코드로 가입 → 담당 학급 확정
 └─ 학부모 초대 코드 발행 (학생 1명당 1개) ┄오프라인 전달┄→ 학부모가 코드로 가입 → 학생 연결 확정
```

| 코드 정책 | 의미 |
|---|---|
| 1회용 | 가입에 한 번 쓰이면 무효 |
| 해시 저장 | 코드 원문을 저장하지 않음 |
| 만료 적용 | 발행 후 일정 기간이 지나면 무효 |
| 시도 제한 | 코드 입력 반복 실패 제한 |
| 응답 통일 | 없는 코드·만료·사용됨을 구분하지 않고 같은 응답 (코드 존재 여부 추측 차단) |
| 공개 가입 경로 없음 | 유효한 초대 코드 없이는 가입 불가 |

**사용자 시나리오**
- 슈퍼 관리자가 앱의 관리자 화면에서 학급을 만들고 학생 명단(이름)을 등록한다. [팀 결정]
- 슈퍼 관리자가 교사 초대 코드를 학급을 지정해 발행한다. [팀 결정]
- 슈퍼 관리자가 학부모 초대 코드를 학생 1명당 1개 발행하고, 학교가 오프라인으로 전달한다. [팀 결정]
- 교사는 초대 코드와 이름·이메일·비밀번호·약관 동의로 가입하고, 지정된 학급의 담임으로 확정된다. [팀 결정][IA]
- 학부모는 초대 코드와 이름·이메일·비밀번호·약관 동의로 가입하고, 해당 학생의 보호자로 확정된다. [팀 결정][IA]
- 가입 시 이메일 인증을 거친다. [IA]
- 재방문 시 로그인하면 저장된 역할의 화면으로 바로 들어간다. [IA]
- 교사는 공개 프로필을 관리하고, 학부모는 홈에서 담임 공개 프로필을 본다. [IA]
- 교사는 학급 관리에서 학부모 연결 현황을 본다. [IA]
- 사용자는 내 정보·연결된 학급·계정을 관리한다. [IA]

**지켜야 할 것**
- 연락처(전화번호·주소)를 받지 않는다. 상대의 이메일도 노출하지 않는다. [원칙 I]
- 식별자는 UUID, 학급·학생 연결 기준으로 건별 권한 검증. [원칙 VII]
- 슈퍼 관리자는 민원 내용(원문·정제본·답변)에 접근할 수 없다. [팀 결정][원칙 VII]
- 로그인·코드 입력 반복 실패 제한, 세션 갱신 시 토큰 회전·재사용 탐지. [원칙, 체크리스트 보안기능 15]
- 기본 계정 없음 — 슈퍼 관리자 계정도 기본값으로 제공하지 않는다. [원칙 VIII]

**IA와 달라지는 점** (`docs/decisions.md` 기록 대상)
- 역할 선택 단계: 코드가 역할을 정하므로 사용자가 고르지 않음
- 학교 검색·학생/교사 이름 입력: 코드가 학급·학생을 정하므로 불필요
- 교사 "코드 재발급"(마이페이지 > 학급 관리): 코드 발행은 슈퍼 관리자 전담
- 신규 역할 "슈퍼 관리자": 기획서 권한표의 "학교 관리자"와 같은 역할로 통합, 코드 발행·명단 관리 추가

**결정됨** [팀 결정 2026-10-15]
- 슈퍼 관리자 계정은 서버에서 직접 생성한다(앱에 생성 경로 없음). 대회용 1차 MVP 범위.
  - 원칙 VIII 적용: 계정 정보를 코드·설정 파일에 하드코딩하지 않고 환경변수로 주입한다.
- 슈퍼 관리자와 기획서의 "학교 관리자"는 **같은 역할**이다. 코드 발행·명단 관리를 맡고, 민원 내용은 볼 수 없다.
- 학생 1명당 보호자 1명만 연결한다.
- 학부모 1명은 **자녀 여럿**을 연결할 수 있다(쌍둥이, 같은 학교 형제자매). 자녀마다 학부모 초대 코드가 따로 발행된다.
- 교사와 학급은 **1:1**이다. 교사 1명은 학급 1개의 담임, 학급 1개의 담임은 1명.
- 초대 코드 **만료 24시간**, 코드 입력 **시도 제한 5회**. 5회를 넘기면 **10분 잠금**, 횟수는 **계정 기준**으로 센다.
  - 가입 화면처럼 계정이 아직 없을 때는 **가입하려는 이메일 기준**으로 센다. IP 기준은 같은 와이파이 사용자끼리 함께 잠기는 위험이 더 커서 택하지 않았다.
- 코드 재발행은 **슈퍼 관리자에게 요청**해서만 가능하다. 앱에 사용자 스스로 재발행하는 경로는 없다. 재발행하면 **이전 코드는 즉시 무효**가 된다.
- 둘째 자녀부터는 이미 가입한 학부모가 앱에서 **코드를 추가 입력**해 연결한다(마이페이지 > 연결된 학급).
- 이메일은 **연락처가 아니다.** 최소한의 인증 수단(가입 인증·로그인 식별)으로만 쓰고, 상대방에게 노출하지 않는다.
- 슈퍼 관리자는 **Flutter 앱 안의 관리자 화면**에서 일한다. 슈퍼 관리자로 로그인하면 관리자 화면이 열린다.
  - 화면: 학급 생성 · 학생 등록(이름) · 교사/학부모 초대 코드 발행 · 발행 현황 · 문의 건수·처리 상태(내용 없음)
  - 서버는 슈퍼 관리자 전용 API를 제공하고, 화면은 이 API만 호출한다.
  - 이유: 인증 방식(Authorization 헤더, 쿠키 미사용)과 네이티브 렌더링을 그대로 유지해 웹 관리 화면이 추가하는 CSRF·XSS 표면을 만들지 않는다.
  - 학급·학생 명단은 슈퍼 관리자가 이 화면에서 등록한다. 등록된 명단은 F3 가명화의 1차 사전이 된다.
  - 초대 코드 원문은 발행 응답에서 한 번만 보여주고, 서버에는 해시만 저장한다.

**미정 — clarify에서 결정**
- [ ] 초대 코드 길이·문자 구성 (이메일 기준 제한은 이메일을 바꿔 우회할 수 있으므로, 코드 자체를 추측 불가능한 길이로 정한다)

## F2. 문의 접수·긴급 분류

**왜**: 학부모의 문의권을 막지 않으면서, 원문을 증거로 남기고, 안전 사안은 어떤 장애에도 즉시 교사에게 닿게 한다.

**사용자 시나리오**
- 학부모가 형식 제약 없이 자유 서술로 문의를 작성한다(길이 상한 있음). [기획][IA]
- 제출된 원문은 그대로 보존되고 이후 수정·삭제할 수 없다. [원칙 III]
- 학생 안전·학대·자해 관련 문의는 정리 단계를 건너뛰고 즉시 교사에게 전달·알림된다. [기획][원칙 IV]
- 학부모는 처리 단계(접수 → 정제 → 교사 확인 → 답변 완료)를 확인한다. [기획][IA]
- 교사는 민원 목록에서 일반/긴급 구분을 본다. [IA]
- 교사가 설정한 응답 가능 시간 밖의 문의는 접수되되 알림은 지연된다. [기획]

**지켜야 할 것**
- 긴급 판정은 외부 AI 호출 전, 규칙 기반, 보수적으로(의심되면 긴급). AI 장애와 무관하게 동작. [원칙 IV]
- 원문 본문을 로그에 남기지 않는다. [원칙 VI]

**미정 — clarify에서 결정**
- [ ] IA "전송 예약 / 예약 목록"이 기획서 "응답 가능 시간(알림 지연)"과 같은 기능인지
- [ ] 민원 "제목" 필드: 학부모가 입력? 정제 결과에서 생성? 가명화 대상인지 (IA 교사 목록에 "제목" 표시)
- [ ] 긴급 판정 시 학부모 화면에 무엇을 보여줄지
- [ ] 문의 길이 상한 값

## F3. 가명화·정제 파이프라인

**왜**: 감정이 실린 문의를 사실관계·요청사항·정서강도로 나눠 교사의 부담을 줄이되, 아동 개인정보는 외부 AI로 나가지 않게 한다.

**사용자 시나리오**
- 일반 문의는 식별정보를 토큰으로 바꾼 뒤 외부 AI로 3요소 분해된다. [기획]
  - 예: "김OO 학생" → `[STUDENT_1]`, "3학년 2반" → `[CLASS_1]`
- 결과는 원래 이름으로 복원되어 교사 화면에 "번역본"으로 표시된다. [IA]
- 교사는 버튼으로 원문을 열람할 수 있고, 열람 사실은 기록된다. [IA][원칙 III]
- 정리 결과가 정해진 형식을 어기면 1회 재시도, 재실패 시 "원문 확인 필요"로 교사에게 알린다. [기획][원칙 IV]
- 요청사항이 불명확하면 학부모에게 보완 질문(되묻기)을 보낸다. [기획]

**지켜야 할 것**
- 가명화 1차: 학급 명단(학생·보호자·교사명)·학교 정보 사전 치환 / 2차: 전화번호·주소 패턴 치환. [기획][원칙 II]
- 복원표는 메모리에만, 저장·로그 금지. [원칙 II]
- AI 출력은 형식 강제 + 서버 재검증, 실행 경로(쿼리 등)에 사용 금지. [원칙 백엔드 요건]
- 검증 안 된 결과는 교사에게 보이지 않는다. [원칙 IV]
- 성능 목표: 문의 접수 ~ 교사 화면 표시 평균 10초 이내. [기획]

**미정 — clarify에서 결정**
- [ ] 되묻기를 MVP에 넣을지 (기획서엔 있고 IA엔 없음), 넣는다면 학부모 응답 화면 흐름
- [ ] 정서강도 표현 방식 (단계 수, 감정 라벨 목록)
- [ ] "원문 확인 필요" 상태에서 교사 화면 구성

## F4. 답변 작성·점검·전송

**왜**: 갈등이 교사 답변에서 다시 불붙지 않게 오해 소지를 미리 짚어주되, 판단과 발송은 교사가 한다.

**사용자 시나리오**
- 교사가 구조화된 문의를 보고 답변을 작성한다. [기획][IA]
- 답변은 가명화 → 점검 → 복원을 거쳐 오해 소지 표현·근거 누락 지점이 표시된다. 관련 규정 첨부를 제안할 수 있다. [기획]
- 교사는 제안을 반영하거나 무시하고 **직접 전송**한다. 점검이 실패해도 원래 답변을 그대로 보낼 수 있다. [기획][원칙 V]
- 학부모는 답변을 받고 알림을 받는다. [IA]

**지켜야 할 것**
- 자동 발송 없음, 시스템이 답변을 대신 고쳐 저장하지 않음. [원칙 V]
- 답변 본문도 암호화 저장, 로그 비출력. [원칙 III·VI]

**미정 — clarify에서 결정**
- [ ] 점검 결과 표시 → 수정 → 전송 화면 상태 (IA엔 "답변 작성"만 있음)
- [ ] "관련 규정 첨부"의 규정 출처 (MVP 포함 여부)
- [ ] 한 문의에 답변 여러 번 가능한지, 학부모 재문의(스레드) 허용 여부

## F5. 감사 로그·이력 보존

**왜**: 분쟁 시 원문·정제본·처리 이력을 변경 불가 형태로 제출할 수 있어야 하고, "검열" 오해를 기록으로 반박할 수 있어야 한다.

**사용자 시나리오**
- 접수·정제·열람·전송 등 모든 처리 단계가 이력으로 남는다. [기획]
- 원문 열람은 누가·언제·무엇을 열람했는지 기록된다. [원칙 III]
- 슈퍼 관리자(= 학교 관리자)는 문의 건수·처리 상태(메타데이터)만 볼 수 있고, 민원 내용은 볼 수 없다. [기획][팀 결정]

**지켜야 할 것**
- 이력·감사 로그는 append-only, 수정·삭제 경로 없음. [원칙 III]
- 로그에는 식별자와 상태만, 본문 없음. [원칙 VI]

**미정 — clarify에서 결정**
- [ ] 이력 조회 화면이 필요한지, 누가 보는지 (교권보호위원회 제출용 내보내기 포함 여부)
