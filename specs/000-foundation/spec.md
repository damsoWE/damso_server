# Feature Specification: 공통 보안·구조 기반 (Foundation)

**Feature Branch**: `feat/000-foundation` (구현 시작 시 생성)

**Created**: 2026-10-15

**Status**: Draft

**Input**: 공통 기반. 사용자 기능이 아니라 이후 모든 기능(F1~F5)이 따르는 보안·구조 기반이다. 에러 응답 정보 비노출, 로그 본문 마스킹, UUID 식별자, 동시 수정 충돌 감지, 민감 필드 자동 암호화, 시크릿 미설정 시 기동 거부, 기본 거부 접근 통제, 진입 지점 입력 검증.

> 이 spec은 최종 사용자(학부모·교사) 기능이 아니다. 여기서 "사용자"는 **이 기반 위에서 기능을 만드는 개발자**, **서버를 띄우는 운영자**, **결과를 검증하는 대회 진단자**다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 진단자가 오류를 유발해도 내부 정보가 보이지 않는다 (Priority: P1)

진단자가 잘못된 형식의 요청, 존재하지 않는 경로, 서버 내부에서 예외가 나는 요청을 보낸다. 어떤 경우든 응답에는 정해진 에러 코드와 일반 메시지만 있고, 스택트레이스·예외 클래스명·서버 내부 경로·쿼리문은 보이지 않는다.

**Why this priority**: 에러 응답은 가장 흔한 정보 유출 경로이고(원칙 VI), 모든 기능의 응답 형식이 이 위에 올라간다. 가장 먼저 있어야 이후 기능이 일관된 에러 형식을 쓴다.

**Independent Test**: 예외를 일부러 던지는 테스트용 경로와 잘못된 요청 몇 종류를 보내고, 모든 응답 본문이 같은 구조이며 금지된 정보가 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 서버가 실행 중, **When** 처리 중 예상하지 못한 내부 오류가 발생, **Then** 응답은 공통 에러 형식(에러 코드 + 일반 메시지)이고 스택트레이스·예외 클래스명·내부 경로·쿼리문을 포함하지 않는다.
2. **Given** 서버가 실행 중, **When** 존재하지 않는 경로로 요청, **Then** 공통 에러 형식의 "찾을 수 없음" 응답을 받는다.
3. **Given** 서버가 실행 중, **When** 허용되지 않은 요청 방식으로 요청, **Then** 공통 에러 형식으로 응답한다.

---

### User Story 2 - 시크릿이 빠지면 서버가 뜨지 않는다 (Priority: P1)

운영자가 필수 시크릿(DB 접속 정보, 암호화 키, 토큰 서명 키, 외부 AI API 키) 중 하나를 빠뜨리거나, 키 길이가 기준에 못 미치는 값을 넣고 서버를 띄운다. 서버는 기동을 거부하고, 어떤 시크릿이 문제인지 이름만 알려준다(값은 출력하지 않는다).

**Why this priority**: 공개 저장소를 그대로 배포했을 때 안전하지 않은 상태로 서버가 뜨는 경로를 막는다(원칙 VIII). 이후 모든 기능이 이 시크릿에 의존한다.

**Independent Test**: 시크릿을 하나씩 빼거나 짧은 키를 넣어 기동해 보고, 매번 기동이 실패하는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 필수 시크릿 중 하나가 없음, **When** 서버 기동, **Then** 기동이 실패하고 누락된 시크릿의 **이름**만 표시된다.
2. **Given** 암호화 키 또는 토큰 서명 키의 길이가 기준 미만, **When** 서버 기동, **Then** 기동이 실패한다.
3. **Given** 모든 필수 시크릿이 기준을 만족, **When** 서버 기동, **Then** 정상 기동한다.
4. **Given** 저장소의 어떤 파일, **When** 시크릿 값을 검색, **Then** 실제 시크릿 값이나 기본 계정·기본 비밀번호가 발견되지 않는다.

---

### User Story 3 - 명시되지 않은 경로는 모두 인증을 요구한다 (Priority: P1)

진단자가 인증 정보 없이 여러 경로를 호출한다. 공개로 지정된 경로 외에는 모두 "인증 필요" 응답을 받는다. 인증은 요청 헤더에 담긴 토큰으로만 이루어지며 쿠키 세션은 만들어지지 않는다.

**Why this priority**: 새 기능을 추가할 때 인증 설정을 빠뜨려도 기본이 "거부"여야 수평 권한상승·무인증 접근이 생기지 않는다(원칙 VII, 체크리스트 보안기능 1).

**Independent Test**: 공개 경로 목록과 그 외 경로를 인증 없이 호출해 결과를 비교하고, 응답에 세션 쿠키가 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 인증 정보 없음, **When** 공개로 지정되지 않은 경로를 호출, **Then** 공통 에러 형식의 "인증 필요" 응답을 받는다.
2. **Given** 인증 정보 없음, **When** 공개로 지정된 경로를 호출, **Then** 정상 응답을 받는다.
3. **Given** 위조되었거나 만료된 토큰, **When** 보호된 경로를 호출, **Then** "인증 필요" 응답을 받는다.
4. **Given** 어떤 요청이든, **When** 응답을 받음, **Then** 세션 쿠키가 설정되지 않는다.

---

### User Story 4 - 민감 본문은 저장소에 평문으로 남지 않는다 (Priority: P2)

개발자가 문의·답변 본문 같은 민감 필드를 "암호화 대상"으로 표시만 하면, 저장할 때 자동으로 암호화되고 읽을 때 복호화된다. 진단자가 저장소를 직접 들여다봐도 평문을 볼 수 없다.

**Why this priority**: 원문 암호화 저장(원칙 III)의 기반이다. F2 문의 접수부터 필요하다.

**Independent Test**: 테스트용 데이터에 민감 필드를 저장한 뒤 저장소 원본 값을 직접 조회해 평문이 아닌지, 애플리케이션으로 다시 읽으면 원래 값인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 암호화 대상으로 표시된 필드, **When** 값을 저장, **Then** 저장소의 원본 값은 평문과 다르다.
2. **Given** 암호화되어 저장된 값, **When** 애플리케이션으로 조회, **Then** 원래 평문을 돌려받는다.
3. **Given** 같은 평문을 두 번 저장, **When** 저장소 원본 값을 비교, **Then** 두 값이 서로 다르다(같은 평문이 같은 암호문으로 드러나지 않음).
4. **Given** 저장된 암호문이 변조됨, **When** 조회, **Then** 변조된 값을 정상 값처럼 돌려주지 않고 오류로 처리한다.

---

### User Story 5 - 민감 본문은 로그에 남지 않는다 (Priority: P2)

개발자가 실수로 민감 본문(문의·답변·정제 결과)을 로그에 넘겨도 로그에는 가려진 값만 남는다. 로그에는 식별자와 상태만 남는다.

**Why this priority**: 로그는 가장 흔한 유출 경로다(원칙 VI). 사람의 실수에 기대지 않고 구조로 막아야 한다.

**Independent Test**: 민감 값을 담은 객체를 로그로 출력하는 테스트를 만들고, 출력된 로그에 원문 문자열이 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 민감 값으로 표시된 데이터, **When** 그 데이터나 그것을 담은 객체를 로그로 출력, **Then** 로그에는 가려진 표시만 남고 원문은 없다.
2. **Given** 요청 처리 중 오류 발생, **When** 오류가 로그에 기록됨, **Then** 요청 본문 원문은 로그에 포함되지 않는다.

---

### User Story 6 - 식별자는 추측할 수 없고, 동시 수정은 충돌로 감지된다 (Priority: P2)

개발자가 새 데이터 종류를 만들 때 공통 기반을 따르면 자동으로 추측 불가능한 식별자를 갖고, 동시 수정 충돌이 감지된다. 진단자는 API 응답의 식별자로 다른 데이터의 식별자를 추측할 수 없다.

**Why this priority**: 순번 식별자는 타인 데이터 추측의 출발점이다(원칙 VII). 상태 전이 경쟁 조건(체크리스트 시간 및 상태 1)은 F2~F4의 상태 변경 전반에 필요하다.

**Independent Test**: 테스트용 데이터를 여러 개 만들어 식별자 형식과 연속성을 확인하고, 같은 데이터를 두 요청이 동시에 수정하게 해 나중 요청이 거부되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 공통 기반을 따르는 데이터, **When** 생성, **Then** 식별자는 UUID 형식이며 연속으로 만든 식별자 사이에 규칙성이 없다.
2. **Given** 같은 데이터를 두 요청이 같은 버전 기준으로 수정, **When** 두 번째 요청이 저장을 시도, **Then** 공통 에러 형식의 "충돌" 응답으로 거부된다.
3. **Given** API 응답, **When** 식별자 필드를 확인, **Then** 내부 순번 값은 노출되지 않는다.

---

### User Story 7 - 잘못된 입력은 진입 지점에서 걸러진다 (Priority: P3)

진단자가 길이 초과, 형식 오류, 필수 값 누락 요청을 보낸다. 요청은 비즈니스 처리 전에 거부되고, 어떤 필드가 왜 틀렸는지 공통 에러 형식으로 알려준다(입력 원문은 응답에 되돌려 보내지 않는다).

**Why this priority**: 각 기능이 자기 입력 규칙을 정하지만, 검증 실패 응답의 형식과 방식은 기반에서 통일해야 한다.

**Independent Test**: 검증 규칙이 걸린 테스트용 경로에 잘못된 입력을 보내 응답 형식을 확인한다.

**Acceptance Scenarios**:

1. **Given** 길이 상한이 있는 필드, **When** 상한을 넘는 값을 보냄, **Then** 처리 전에 거부되고 공통 에러 형식으로 해당 필드 이름과 위반 사유가 응답된다.
2. **Given** 형식이 맞지 않는 본문(깨진 구조), **When** 요청, **Then** 공통 에러 형식으로 거부되고 파서 내부 메시지는 노출되지 않는다.

---

### Edge Cases

- 에러 메시지를 만드는 과정 자체에서 오류가 나면? → 그래도 최소한의 공통 에러 형식("내부 오류")으로 응답한다.
- 암호화 키가 바뀌면 기존 암호문은? → 이번 범위에서는 키 교체를 지원하지 않는다. 키가 다르면 복호화 실패로 처리하고 평문을 추측해 돌려주지 않는다.
- 민감 필드에 빈 값이 들어오면? → 빈 값은 빈 값으로 저장·조회된다(암호화 대상이 아님).
- 로그 출력 시 민감 값이 문자열로 직접 이어 붙여지면? → 구조로 막을 수 있는 범위(민감 값 타입의 문자열 표현)는 가리고, 문자열 직접 결합은 코드 리뷰·정적 분석 대상으로 둔다.
- 공개 경로에 인증 토큰이 함께 오면? → 토큰이 잘못돼도 공개 경로는 정상 처리한다.
- 요청 본문이 매우 큰 경우? → 정해진 최대 크기를 넘으면 처리 전에 거부한다.

## Requirements *(mandatory)*

### Functional Requirements

**에러 처리** (원칙 VI · 체크리스트 에러처리 1·3)

- **FR-001**: 시스템은 모든 오류 응답을 하나의 공통 형식(에러 코드, 일반 메시지, 필요 시 필드별 검증 오류 목록)으로 반환해야 한다.
- **FR-002**: 오류 응답은 스택트레이스, 예외 클래스명, 서버 내부 경로, 쿼리문, 프레임워크 기본 오류 페이지를 포함해서는 안 된다.
- **FR-003**: 예상하지 못한 오류도 공통 형식의 "내부 오류"로 응답해야 하며, 상세 원인은 서버 내부 로그에만 남긴다(민감 본문 제외).
- **FR-004**: 시스템은 공통 에러 코드 목록을 제공해야 한다. 최소: 잘못된 입력, 인증 필요, 권한 없음, 찾을 수 없음, 충돌, 허용되지 않은 요청 방식, 요청 크기 초과, 내부 오류.

**로그** (원칙 VI · 체크리스트 캡슐화 2)

- **FR-005**: 시스템은 민감 값을 표시하는 수단을 제공해야 하며, 표시된 값은 어떤 로그 출력에서도 가려진 형태로만 나타나야 한다.
- **FR-006**: 요청·응답 본문을 자동으로 로그에 남기는 동작은 꺼져 있어야 한다.
- **FR-007**: 시스템은 디버그용 진단 화면·API 문서 화면을 제공하지 않으며, 서버 상태 확인 외의 진단 정보(설정값·빈 목록·환경변수 등)를 외부에 노출하지 않아야 한다. API 문서 화면을 나중에 도입하면 기본 비활성으로 둔다.

**식별자·동시성** (원칙 VII · 체크리스트 시간 및 상태 1)

- **FR-008**: 시스템은 모든 데이터가 상속하는 공통 기반을 제공해야 하며, 이 기반은 추측 불가능한 UUID 식별자와 생성·수정 시각을 갖는다.
- **FR-009**: API로 노출되는 식별자는 UUID만 허용한다.
- **FR-010**: 공통 기반은 수정 버전을 관리해, 같은 버전을 기준으로 한 두 번째 수정을 "충돌"로 거부해야 한다.

**암호화** (원칙 III · 체크리스트 보안기능 4·5·8)

- **FR-011**: 시스템은 필드를 "암호화 대상"으로 표시하면 저장 시 자동 암호화, 조회 시 자동 복호화하는 수단을 제공해야 한다.
- **FR-012**: 암호화는 256비트 키의 인증된 암호화 방식을 사용해, 같은 평문도 매번 다른 암호문이 되고 변조가 감지되어야 한다.
- **FR-013**: 암호화에 쓰이는 난수는 암호학적으로 안전한 난수 생성기에서 만들어야 한다.

**시크릿·기동** (원칙 VIII · 체크리스트 보안기능 6·7)

- **FR-014**: 필수 시크릿(DB 접속 정보, 컬럼 암호화 키, 토큰 서명 키, 외부 AI API 키)은 환경변수로만 주입받아야 하며, 코드·설정 파일에 값이 있어서는 안 된다.
- **FR-015**: 필수 시크릿이 하나라도 없거나, 암호화 키·토큰 서명 키가 256비트 미만이면 서버는 기동을 거부해야 한다.
- **FR-016**: 기동 거부 시 누락·부적합 시크릿의 **이름**만 출력하고 값은 출력하지 않아야 한다.
- **FR-017**: 시스템은 기본 계정·기본 비밀번호를 제공하지 않아야 한다.
- **FR-018**: 저장소에는 필요한 환경변수의 **이름**만 담은 예시 파일을 둔다.

**접근 통제** (원칙 VII · 체크리스트 보안기능 1·10, 입력 11)

- **FR-019**: 공개로 명시된 경로(이번 범위: 서버 상태 확인) 외의 모든 경로는 인증을 요구해야 한다(기본 거부).
- **FR-020**: 인증은 요청 헤더의 토큰으로만 이루어지며, 서버는 세션을 만들거나 세션 쿠키를 발급하지 않아야 한다.
- **FR-021**: 토큰 검증은 서명 알고리즘을 고정하고, 서명 없는 토큰·위조 토큰·만료 토큰을 거부해야 한다.
- **FR-022**: 인증 실패는 "인증 필요", 인가 실패는 "권한 없음" 공통 에러 형식으로 응답해야 한다.

**입력 검증** (체크리스트 입력 14, 에러처리 1)

- **FR-023**: 요청 입력은 비즈니스 처리 전에 선언된 규칙(필수 여부·길이·형식·범위)으로 검증되어야 한다.
- **FR-024**: 검증 실패 응답은 필드 이름과 위반 사유를 담되, 입력 원문은 되돌려 보내지 않아야 한다.
- **FR-025**: 요청 본문의 최대 크기를 정하고, 넘으면 처리 전에 거부해야 한다.

**보안약점 체크리스트 연결**

- **FR-026**: 이 기반이 완료되면 `docs/security-checklist.md`의 다음 항목을 근거(코드 위치·테스트 이름)와 함께 `조치`로 갱신해야 한다: 에러처리 1·3, 보안기능 1·4·5·6·7·8·10, 시간 및 상태 1, 캡슐화 2, 입력데이터 검증 14.

### Key Entities

- **공통 데이터 기반**: 모든 데이터가 갖는 공통 속성. UUID 식별자, 생성 시각, 수정 시각, 수정 버전.
- **공통 에러 응답**: 에러 코드, 일반 메시지, (검증 실패 시) 필드별 오류 목록.
- **에러 코드 목록**: 시스템 전체에서 쓰는 에러 코드와 그에 대응하는 응답 상태의 고정된 목록.
- **필수 시크릿 목록**: 기동 시 검증하는 시크릿 이름과 각각의 최소 요건(존재 여부, 최소 길이).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 자동화 테스트로 유발한 모든 오류 응답(최소 8종: 에러 코드 목록 전부) 중 스택트레이스·예외 클래스명·내부 경로·쿼리문이 포함된 응답이 0건이다.
- **SC-002**: 필수 시크릿 6개(환경변수 기준) 각각을 빼거나 기준 미달 값으로 바꾼 기동 시도에서 기동 거부율이 100%이고, 출력에 시크릿 값이 포함된 경우가 0건이다.
- **SC-003**: 공개 경로를 제외한 모든 경로를 인증 없이 호출했을 때 "인증 필요" 응답률이 100%이고, 응답에 세션 쿠키가 설정된 경우가 0건이다.
- **SC-004**: 암호화 대상 필드를 저장한 뒤 저장소 원본을 조회했을 때 평문과 일치하는 값이 0건이고, 애플리케이션 조회 결과는 100% 원래 값과 일치한다.
- **SC-005**: 민감 값을 로그로 출력하는 테스트에서 로그에 원문이 포함된 경우가 0건이다.
- **SC-006**: 동시 수정 테스트에서 같은 버전 기준 두 번째 수정이 거부되는 비율이 100%이다.
- **SC-007**: 저장소 전체에 대한 시크릿 스캔 결과 검출 0건을 유지한다.
- **SC-008**: `docs/security-checklist.md`에서 FR-026에 나열된 12개 항목이 모두 근거와 함께 `조치` 상태가 된다.
- **SC-009**: 새 기능을 만드는 개발자가 공통 기반을 상속·표시만 해서 UUID 식별자·동시성 검사·암호화·로그 가림을 얻는다(기능 코드에 암호화·마스킹 로직을 직접 쓰는 곳 0곳).

## Assumptions

- 토큰 **발급**(로그인·갱신·회전)은 F1 범위다. 이 기반은 헤더 토큰 **검증**과 기본 거부 구조만 제공하며, 테스트는 테스트용으로 서명한 토큰으로 한다.
- 이번 범위의 공개 경로는 서버 상태 확인 하나뿐이다. 회원가입·로그인 등 공개 경로는 각 기능에서 명시적으로 추가한다.
- 타인 데이터 접근 시 "권한 없음"과 "찾을 수 없음" 중 무엇으로 응답할지(존재 여부 노출 방지)는 각 기능 spec에서 정한다. 기반은 두 에러 코드를 모두 제공한다.
- 컬럼 암호화 키 교체(로테이션)는 MVP 범위 밖이다.
- 키 길이 기준은 256비트다(기획서의 AES-256과 일치).
- 요청 본문 최대 크기 기본값은 문의 본문 상한(2,000자)을 여유 있게 담는 수준으로 plan에서 정한다.
- 감사 로그 저장(F5), 가명화(F3), 회원·인증 기능(F1)은 범위 밖이다.
- 이 spec의 문서 언어는 한국어다(constitution 개발 흐름).
