### Session 2026-10-25

- 입력(`docs/features.md` F3 "결정됨", 팀 결정 2026-10-15): 되묻기는 MVP 제외. 정서강도는 3단계(낮음·보통·높음) + 고정 목록(불안·불만·분노·걱정·답답함·슬픔)에서 라벨 최대 2개. "원문 확인 필요" 상태에서는 안내 + 원문 열람 버튼(열람 기록) + 재시도 버튼을 보여 주고, 교사 재시도는 문의 1건당 1회이며 자동 재시도 1회 + 교사 재시도 1회 후에도 실패하면 원문 확인만 가능하다.
- Q: F2가 비워 둔 위기 종류 분류(자해·학대·그 밖의 안전)를 F3에서 채우나? → A: A. F3에 포함한다. 긴급 문의의 위기 종류를 가려진 원문으로 분류해 F2의 연결 지점으로 넘기고, 학부모 안내가 종류에 맞는 번호만 보이게 한다. 분류가 실패하거나 늦어도 긴급 전달은 분류를 기다리지 않는다. (이슈 #6의 작업 항목에도 추가한다.)
- Q: 일반 문의의 교사 알림은 언제 가나? → A: B. 정리가 확정됐을 때(검증을 통과해 번역본이 생겼거나, 자동 재시도까지 실패해 "원문 확인 필요"가 확정됐을 때) 보낸다. 접수 즉시 보내던 F2의 일반 문의 알림 규칙을 이에 맞게 고친다. 긴급 문의 알림은 바뀌지 않는다.
- Q: 일반 문의에서 "교사 확인" 단계로 넘어가는 기준은? → A: A. 교사가 번역본을 처음 열람한 때다. 번역본이 없는 "원문 확인 필요" 문의는 교사가 원문을 처음 열람한 때로 본다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 일반 문의의 식별정보를 가린 뒤 외부 AI로 정리한다 (Priority: P1)

학부모가 일반 문의를 접수하면 시스템이 문의 속 식별정보(학생·보호자·교사 이름, 학교·학급, 전화번호, 주소)를 토큰으로 바꾼 뒤, 가려진 글만 외부 AI에 보내 사실관계·요청사항·정서강도 세 가지로 나눈다. 외부 AI는 어떤 경우에도 가려지지 않은 원문을 받지 않는다.

**Why this priority**: 아동 개인정보가 외부 경계를 넘지 않게 하는 것이 이 기능의 존재 이유다(원칙 II). 이것이 없으면 정제 결과를 만들 수 없고, 있어도 안전하지 않다.

**Independent Test**: 학생·학급·전화번호가 들어 있는 일반 문의를 접수하고, 외부 AI로 나간 글에 원래 식별정보가 한 글자도 없는지, 정리 결과가 3요소로 나뉘는지 확인한다.

**Acceptance Scenarios**:

1. **Given** "김OO 학생" 같은 학급 명단의 이름이 들어 있는 일반 문의, **When** 정리 처리, **Then** 외부로 나가는 글에서 이름이 `[STUDENT_1]` 같은 토큰으로 바뀌어 있다.
2. **Given** "3학년 2반"처럼 학교·학급 정보가 들어 있는 문의, **When** 정리 처리, **Then** 학급·학교 정보가 토큰(`[CLASS_1]` 등)으로 바뀐다.
3. **Given** 학급 명단에 없지만 전화번호·주소 형태로 쓰인 글, **When** 정리 처리, **Then** 패턴으로 찾아 토큰으로 바꾼다(2차 치환).
4. **Given** 같은 이름이 문의 안에 여러 번 나옴, **When** 정리 처리, **Then** 같은 토큰으로 일관되게 바뀐다.
5. **Given** 가명화 단계가 실패하거나 중단됨, **When** 정리 처리, **Then** 외부 AI는 호출되지 않는다(가리지 못한 글은 나가지 않는다).
6. **Given** 정리가 끝난 문의, **When** 저장소·로그·오류 응답을 점검, **Then** 토큰과 원래 값의 대응표는 어디에도 남아 있지 않다.
7. **Given** 일반 문의가 접수됨, **When** 처리 단계를 점검, **Then** 정리는 접수 응답을 기다리게 하지 않고 뒤에서 진행된다.

### User Story 2 - 교사가 정리된 "번역본"을 원래 이름으로 본다 (Priority: P1)

정리가 끝나면 교사 화면에는 "번역본"이 보인다. 번역본은 사실관계·요청사항·정서강도(3단계 + 감정 라벨 최대 2개)로 구성되고, 토큰은 원래 이름·학급으로 되돌려져 읽기 쉽다. 번역본은 문의 목록의 제목 자리에도 쓰일 짧은 제목을 함께 가진다.

**Why this priority**: 교사의 부담을 줄이는 것이 목적이므로, 정리 결과가 교사에게 보이는 것이 이 기능의 핵심 가치다.

**Independent Test**: 정리가 완료된 일반 문의를 교사 계정으로 열어, 3요소·정서강도·라벨·제목이 보이고 토큰이 남아 있지 않은지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정리가 완료된 일반 문의, **When** 교사가 상세를 열면, **Then** "번역본"으로 사실관계·요청사항·정서강도가 보인다.
2. **Given** 정리 결과에 `[STUDENT_1]` 토큰이 들어 있음, **When** 교사 화면에 표시, **Then** 원래 학생 이름으로 되돌려져 보이고 토큰 문자열은 화면에 없다.
3. **Given** 정서강도, **When** 교사가 확인, **Then** 낮음·보통·높음 중 하나이고, 감정 라벨은 불안·불만·분노·걱정·답답함·슬픔 중 최대 2개다.
4. **Given** 정리가 아직 끝나지 않은 일반 문의, **When** 교사가 목록을 열면, **Then** 고정 문구 제목으로 보이고 정리 결과는 보이지 않는다.
5. **Given** 정리 결과의 제목, **When** 목록에 표시, **Then** 정리 결과에서 자동 생성된 제목이 보이고, 정리 전에는 고정 문구가 보인다.
6. **Given** 다른 학급의 문의, **When** 교사가 번역본 조회를 시도, **Then** 거부된다(F2의 건별 소유권 규칙).
7. **Given** 정리 결과를 교사에게 보여 줄 때, **When** 응답을 점검, **Then** 학부모의 이메일·연락처는 없다.
8. **Given** 정리가 완료된 일반 문의, **When** 교사가 번역본을 처음 열람, **Then** 처리 단계가 "교사 확인"으로 바뀌고 열람 시각이 단계 이력에 남는다. 두 번째 열람부터는 단계가 바뀌지 않는다.
9. **Given** 두 교사 요청이 번역본을 거의 동시에 처음 열람, **When** 요청이 도착, **Then** "교사 확인" 단계는 한 번만 기록된다.

### User Story 3 - 정리가 실패하면 검증 안 된 결과를 숨기고 원문 확인으로 안전하게 넘긴다 (Priority: P1)

외부 AI의 결과가 정해진 형식을 어기거나 허용된 값이 아니면 그 결과는 버려지고 1회 자동 재시도한다. 다시 실패하면 문의는 "원문 확인 필요" 상태가 되고 교사에게 알린다. 교사 화면에는 "자동 정리에 실패했습니다. 원문을 확인해 주세요" 안내, 원문 열람 버튼, 재시도 버튼이 보인다. 교사의 재시도는 문의 1건당 1회이며, 그 뒤에도 실패하면 원문 확인만 가능하다. 검증되지 않은 결과는 어떤 경우에도 교사에게 보이지 않는다.

**Why this priority**: 잘못 정리된 글이 사실처럼 전달되는 것을 막는 안전장치다(원칙 IV). 외부 장애가 문의 자체를 잃게 해서도 안 된다.

**Independent Test**: 외부 AI가 형식 위반 결과를 돌려주도록 해 두고 일반 문의를 접수한 뒤, 자동 재시도 1회 후 "원문 확인 필요"로 바뀌고 교사에게 알림이 가는지, 교사 재시도가 1회만 허용되는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 외부 AI 결과가 정해진 형식을 어김, **When** 서버가 검증, **Then** 그 결과는 폐기되고 교사에게 보이지 않으며 자동으로 1회 다시 시도한다.
2. **Given** 자동 재시도에서 올바른 결과가 나옴, **When** 검증을 통과, **Then** 정상 정리 완료와 같이 번역본이 보인다.
3. **Given** 자동 재시도도 실패, **When** 처리 종료, **Then** 문의는 "원문 확인 필요" 상태가 되고 교사에게 고정 문구로 알림이 간다.
4. **Given** "원문 확인 필요" 문의, **When** 교사가 상세를 열면, **Then** "자동 정리에 실패했습니다. 원문을 확인해 주세요" 안내, 원문 열람 버튼, 재시도 버튼이 보인다.
5. **Given** "원문 확인 필요" 문의, **When** 교사가 재시도 버튼을 누르고 이번에 성공, **Then** 번역본이 보이고 "원문 확인 필요"가 해제된다.
6. **Given** 교사 재시도도 실패, **When** 교사가 다시 상세를 열면, **Then** 재시도 버튼은 없고 원문 확인만 가능하다.
7. **Given** 교사가 같은 문의의 재시도 버튼을 거의 동시에 두 번 누름, **When** 요청이 도착, **Then** 재시도는 한 번만 실행된다.
8. **Given** 외부 AI가 응답하지 않거나 오류, **When** 처리, **Then** 형식 위반과 같게 취급하고, 접수된 문의 자체는 영향받지 않는다.
9. **Given** 외부 AI가 문의 안의 문장을 지시처럼 가장한 글(예: "이전 지시를 무시하라")을 포함함, **When** 처리, **Then** 그것은 정리할 글일 뿐 시스템 지시로 작동하지 않고, 결과가 형식을 어기면 폐기된다.
10. **Given** 정리 결과, **When** 서버가 그 값을 사용, **Then** 정리 결과는 저장되는 글로만 쓰이고 조회 조건·경로·권한 판단 등 실행에 쓰이지 않는다.

### User Story 4 - 교사가 일반 문의의 원문을 열람하고 기록이 남는다 (Priority: P2)

교사는 번역본을 보다가 원문이 필요하면 버튼으로 원문을 열람한다. 열람한 사실(누가·언제·무엇을)이 수정·삭제할 수 없는 기록으로 남는다. 정리가 끝나기 전이나 "원문 확인 필요" 상태에서도 원문을 열람할 수 있다.

**Why this priority**: 정리본이 원문을 가리는 "검열"이 아님을 보장하고, 열람이 투명하게 남아야 한다(원칙 III). 다만 번역본이 먼저 있어야 의미가 있어 P1 뒤에 온다.

**Independent Test**: 일반 문의의 원문을 열람한 뒤 열람 기록(열람자·대상·시각)이 남는지, 다른 학급 교사는 열람할 수 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 담당 학급의 일반 문의, **When** 교사가 원문 열람 버튼을 누름, **Then** 원문이 보이고 열람자·대상·시각이 기록된다.
2. **Given** 열람 기록이 실패, **When** 원문 열람 시도, **Then** 원문은 보이지 않는다(기록 없이 원문이 나가지 않는다).
3. **Given** 정리 전이거나 "원문 확인 필요"인 문의, **When** 교사가 원문 열람, **Then** 열람할 수 있다.
3a. **Given** 번역본이 없는 "원문 확인 필요" 문의, **When** 교사가 원문을 처음 열람, **Then** 처리 단계가 "교사 확인"으로 바뀐다. 번역본이 있는 문의는 원문을 열람해도 단계가 바뀌지 않는다(번역본 첫 열람이 기준이다).
4. **Given** 같은 문의를 같은 교사가 두 번 열람, **When** 기록을 점검, **Then** 열람마다 기록이 남는다.
5. **Given** 다른 학급의 문의나 슈퍼 관리자, **When** 원문 열람 시도, **Then** 거부된다.
6. **Given** 열람 기록, **When** 누구든 수정·삭제를 시도, **Then** 그런 기능은 없다.

### User Story 5 - 학부모가 정제·교사 확인 단계까지의 진행을 확인한다 (Priority: P2)

학부모는 문의 상세의 타임라인에서 일반 문의가 접수된 뒤 정제, 교사 확인 단계까지 진행됐는지 시각과 함께 본다. 학부모에게는 정리 결과(번역본)나 정서강도를 보여 주지 않고, 단계와 시각만 보인다.

**Why this priority**: 학부모가 문의가 어디까지 갔는지 알아야 불안이 줄지만, 정리 자체가 먼저다.

**Independent Test**: 일반 문의를 접수하고 정리가 끝난 뒤 학부모 상세에서 "정제" 단계가 시각과 함께 보이고 정리 결과는 보이지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 정리가 완료된 일반 문의, **When** 학부모가 상세를 열면, **Then** 타임라인에 "접수" 다음으로 "정제"가 시각과 함께 보인다.
1a. **Given** 교사가 번역본을 처음 열람한 일반 문의, **When** 학부모가 상세를 열면, **Then** 타임라인에 "교사 확인"이 시각과 함께 보인다.
2. **Given** "원문 확인 필요"가 된 문의, **When** 학부모가 상세를 열면, **Then** 정제 완료로 보이지 않고, 실패했다는 사실이나 내부 사유는 노출되지 않는다.
3. **Given** 학부모 응답, **When** 점검, **Then** 정리 결과·정서강도·감정 라벨은 없다.
4. **Given** 다른 학부모의 문의, **When** 조회 시도, **Then** 거부된다.
5. **Given** 정제 단계 전이, **When** 같은 문의에 동시 변경이 오면, **Then** 한 번에 하나만 성공한다.

### User Story 6 - 긴급 문의의 위기 종류를 분류해 학부모 안내에 연결한다 (Priority: P2)

긴급 판정과 교사 전달이 끝난 뒤, 시스템이 식별정보를 가린 원문으로 위기 종류(자해 / 학대 / 그 밖의 안전)만 고른다. 그 결과를 F2가 만든 연결 지점으로 넘기면 학부모 화면에 종류에 맞는 번호만 고정 문구로 보인다. 분류가 실패하거나 늦으면 기본 안내(112·109 함께)가 그대로 보이고, 긴급 전달과 교사 알림은 어떤 경우에도 분류를 기다리지 않는다.

**Why this priority**: 모든 안전 문의에 번호 세 개를 한꺼번에 보여 주면 학부모에게 위압적이다. 다만 교사 전달이 먼저이고 분류는 보조 안내이므로 정제(P1) 뒤에 온다.

**Independent Test**: 긴급 문의를 접수하고 외부 AI가 종류를 돌려주는 경우, 실패·지연되는 경우, 허용되지 않은 값을 돌려주는 경우 각각 학부모 안내가 맞게 보이는지, 외부 AI가 꺼져 있어도 긴급 전달이 정상인지 확인한다.

**Acceptance Scenarios**:

1. **Given** 자해로 분류된 긴급 문의, **When** 학부모 화면, **Then** "선생님께 바로 전달했어요"와 자살예방 상담전화 109만 보인다.
2. **Given** 학대로 분류된 긴급 문의, **When** 학부모 화면, **Then** 같은 안내와 아동학대 신고 112만 보인다.
3. **Given** 그 밖의 안전으로 분류된 긴급 문의, **When** 학부모 화면, **Then** 번호 없이 전달 안내만 보인다.
4. **Given** 분류가 실패·지연됨, **When** 학부모 화면, **Then** 기본 안내(112·109 함께)가 바로 보이고 교사 전달·알림은 영향받지 않는다.
5. **Given** 외부 AI의 분류 결과가 허용된 값이 아님, **When** 처리, **Then** 그 값은 버리고 "분류 안 됨"으로 본다.
6. **Given** 분류에 보내는 글, **When** 점검, **Then** 일반 정리와 같이 식별정보가 가려진 글만 나간다.
7. **Given** 분류가 늦게 끝남, **When** 학부모가 화면을 다시 열면, **Then** 이미 본 기본 안내가 종류에 맞는 안내로 바뀌어 보인다.
8. **Given** 위기 종류가 분류됨, **When** 긴급 표시·교사 전달·알림을 점검, **Then** 분류 결과는 그것들을 바꾸지 않는다.

### User Story 7 - 정리가 확정된 뒤에 교사에게 일반 문의 알림이 간다 (Priority: P1)

일반 문의의 교사 알림은 접수 즉시가 아니라 정리가 확정됐을 때 간다. 검증을 통과한 번역본이 생겼거나, 자동 재시도까지 실패해 "원문 확인 필요"가 확정되면 교사에게 고정 문구로 한 번 알린다. 그래서 교사가 알림을 보고 열었을 때 항상 번역본이나 실패 안내가 보인다. 응답 가능 시간 지연, 일반 알림 끄기, 묶음 알림 같은 F2의 알림 규칙은 그대로 적용하되 "보낼 시점"이 정리 확정 시점이 된다. 긴급 문의 알림은 바뀌지 않는다.

**Why this priority**: 알림을 받은 교사가 빈 화면을 보게 하면 정리의 의미가 없어진다. 접수 즉시 알림이 가던 F2 동작을 바꾸는 일이라 정리와 함께 있어야 한다.

**Independent Test**: 일반 문의를 접수해 정리가 끝나기 전에는 알림이 없고, 끝난 뒤에 한 번 가는지 확인한다. 정리가 실패로 확정되는 경우와 응답 가능 시간 밖인 경우도 확인한다.

**Acceptance Scenarios**:

1. **Given** 접수된 일반 문의의 정리가 아직 진행 중, **When** 시간이 흐름, **Then** 교사에게 알림이 가지 않는다.
2. **Given** 정리가 검증을 통과해 번역본이 생김, **When** 정리 확정, **Then** 교사에게 고정 문구로 알림이 한 번 간다.
3. **Given** 자동 재시도까지 실패해 "원문 확인 필요"가 확정됨, **When** 확정, **Then** 교사에게 고정 문구로 알림이 한 번 간다.
4. **Given** 교사 재시도가 나중에 성공함, **When** 번역본이 생김, **Then** 같은 문의로는 추가 알림이 가지 않는다.
5. **Given** 정리가 확정된 시각이 응답 가능 시간 밖, **When** 확정, **Then** 알림은 다음 응답 가능 시간이 시작될 때로 미뤄지고 그동안 쌓인 일반 문의는 묶어 고정 문구 + 건수로 한 번만 간다.
6. **Given** 교사가 일반 알림을 꺼 둠, **When** 정리 확정, **Then** 알림은 가지 않고 문의는 목록에 그대로 남는다.
7. **Given** 긴급 문의, **When** 접수, **Then** 알림은 F2와 같이 즉시 가고 정리 확정을 기다리지 않는다.
8. **Given** 외부 AI 장애로 정리가 오래 걸림, **When** 처리 시간 상한을 넘김, **Then** 응답 없음으로 보고 자동 재시도하며, 실패가 확정되면 알림이 가서 알림이 영영 나가지 않는 일이 없다.

### Edge Cases

- 학급 명단에 없는 이름(다른 학부모·친구 이름 등)이나 패턴에 맞지 않는 식별정보는 1차·2차 치환으로 찾지 못할 수 있다. 이 한계는 알려진 것으로 두고, 가려지지 않은 채 나갈 수 있는 정보의 범위를 plan 단계에서 명시한다(Assumptions 참조).
- 본문이 매우 짧거나("네", "감사합니다") 정리할 사실이 없는 글은 형식에 맞게 빈 요소 없이 정리되거나 실패로 처리되며, 어느 쪽이든 교사에게 검증되지 않은 문장은 보이지 않는다.
- 같은 문의에 대한 정리 요청이 중복으로 시작되어도(재배포·재시작 등) 정제 단계는 한 번만 기록되고 결과는 하나만 남는다.
- 긴급으로 판정된 문의는 정제를 건너뛴다. 정제 대상이 아닌 문의에 정리 결과를 만들지 않는다.
- 정리가 진행되는 동안 담임이 바뀌면, 결과는 문의의 담당 학급 기준으로 새 담임이 본다(F2: 접수 시점 학급 기준, 현재 담임이 열람).
- 외부 AI 장애가 길어져도 접수·긴급 전달·목록·원문 열람은 정상 동작한다. 영향받는 것은 번역본과, 그에 묶인 일반 문의 알림(처리 시간 상한 뒤 실패로 확정되면 알림이 간다)이다.
- "원문 확인 필요"로 확정된 문의는 교사가 원문을 처음 열람할 때 "교사 확인"이 된다(접수 → 교사 확인). 그 뒤 교사 재시도가 성공해 번역본이 생겨도 이미 "교사 확인" 이후이므로 "정제" 단계는 추가하지 않는다(단계는 앞으로만 간다). 번역본은 교사에게 보이고 재시도 한도(1회)는 그대로 적용된다.
- 응답 가능 시간 판정은 알림을 보낼 시점(정리 확정 시각) 기준이다. 학부모에게 접수 때 보이는 "선생님 응답 가능 시간에 전달됩니다" 안내는 접수 시각 기준의 참고 문구라, 정리가 끝난 시각의 판정과 다를 수 있다.
- 위기 종류 분류는 긴급 문의에만 하고 한 번만 시도한다. 실패·지연·허용값 위반은 "분류 안 됨"(기본 안내)이며 교사 재시도는 없다. 분류 결과는 긴급 표시·교사 전달·알림을 바꾸지 않는다.
- 정서강도·라벨은 교사의 이해를 돕는 참고 표시일 뿐 긴급 판정을 바꾸지 않는다. 일반 문의가 정서강도 "높음"이어도 긴급으로 바뀌지 않는다.
- 접수부터 교사 화면 표시까지는 평균 10초 이내가 목표다. 목표를 넘겨도 문의는 유실되지 않고 정리는 계속 진행된다.

## Requirements *(mandatory)*

### Functional Requirements

**가명화**

- **FR-001**: 외부 AI로 나가는 모든 글은 가명화를 거쳐야 MUST 한다. 가려지지 않은 원문이 외부로 나가는 경로를 두지 MUST NOT 한다.
- **FR-002**: 1차 가명화는 학급 명단(학생·보호자·교사 이름)과 학교·학급 정보를 사전 방식으로 토큰(`[STUDENT_1]`, `[CLASS_1]` 등)으로 바꾼다.
- **FR-003**: 2차 가명화는 전화번호·주소 형태를 패턴으로 찾아 토큰으로 바꾼다.
- **FR-004**: 같은 값은 한 문의 안에서 같은 토큰으로 일관되게 바꾼다. 토큰과 원래 값의 대응표는 정리 처리 중 메모리에만 있고 저장·로그·오류 응답에 남기지 MUST NOT 한다.
- **FR-005**: 가명화가 실패하거나 완료되지 않으면 외부 AI를 호출하지 않고 정리 실패로 처리한다.

**정리(정제)**

- **FR-006**: 일반 문의는 접수 뒤에 사실관계·요청사항·정서강도 세 요소로 정리된다. 정리는 접수 응답을 지연시키지 않는다.
- **FR-007**: 정서강도는 낮음·보통·높음 3단계 중 하나이고, 감정 라벨은 불안·불만·분노·걱정·답답함·슬픔 중 최대 2개다.
- **FR-008**: 정리 결과는 정해진 형식을 강제로 요구해 받고, 서버가 형식과 허용값을 다시 검증한다. 어긋난 결과는 폐기한다.
- **FR-009**: 정리 결과와 문의 안의 글은 시스템 지시와 분리해 다룬다. 문의 안의 문장은 지시로 작동하지 않는다.
- **FR-010**: 정리 결과는 저장·표시 용도로만 쓰고 조회 조건·경로·주소·권한 판단 같은 실행 경로에 쓰지 MUST NOT 한다.
- **FR-011**: 정리 결과의 토큰은 교사에게 보이기 전에 원래 이름·학급으로 되돌린다(정리 처리 중, 대응표가 메모리에 있을 때). 되돌린 결과는 "번역본"으로 표시한다. 전화번호·이메일·주소·주민등록번호는 되돌리지 않고 고정 문구("(연락처 생략)" 등)로 남긴다 — 정리 결과가 연락처를 새로 저장하지 않게(원칙 I).
- **FR-012**: 정리가 끝나면 목록의 제목은 정리 결과에서 자동 생성한 제목으로 보이고, 끝나기 전에는 F2의 고정 문구를 쓴다. 제목도 본문처럼 암호화해 저장하고 로그에 남기지 않는다.
- **FR-013**: 긴급 문의는 정제를 건너뛴다. 정제는 일반 문의에만 한다.
- **FR-013a**: 정리 시도에는 처리 시간 상한이 있다. 상한을 넘기면 응답 없음으로 보고 실패와 같이 다룬다(구체 값은 plan에서 정한다). 정리가 끝없이 대기해 알림이나 "원문 확인 필요" 전이가 영영 일어나지 않는 일이 없어야 한다.

**실패 처리**

- **FR-014**: 정리 결과가 검증에 실패하거나 외부 AI가 응답하지 않으면 자동으로 1회 다시 시도한다.
- **FR-015**: 자동 재시도도 실패하면 문의는 "원문 확인 필요" 상태가 되고 교사에게 고정 문구로 알린다. 검증되지 않은 정리 결과는 교사에게 보이지 MUST NOT 한다.
- **FR-016**: "원문 확인 필요" 문의의 교사 화면에는 "자동 정리에 실패했습니다. 원문을 확인해 주세요" 안내, 원문 열람 버튼, 재시도 버튼을 보여 준다.
- **FR-017**: 교사의 재시도는 문의 1건당 1회다. 자동 재시도 1회와 교사 재시도 1회 후에도 실패하면 원문 확인만 가능하다. 재시도 요청이 동시에 여러 번 와도 한 번만 실행한다. **F5에서 변경(2026-10-28)**: 받아들여진 재시도는 누가 요청했는지 기록한다. 기록은 재시도가 커밋된 뒤 요청 시각으로 남기며, 기록이 실패해도 재시도는 정상 진행(202)되고 서버 로그(문의 ID·행위 종류·오류 종류)만 남는다 (`specs/006-audit-log-history` FR-005·006, research R9).
- **FR-018**: 정리 실패나 외부 AI 장애는 접수된 문의·원문·긴급 경로·목록에 영향을 주지 않는다.

**원문 열람·기록**

- **FR-019**: 교사는 담당 학급 일반 문의의 원문을 정리 상태와 상관없이 열람할 수 있다. 열람은 열람자·대상·시각이 수정·삭제할 수 없는 기록으로 남고, 기록이 실패하면 원문을 보여 주지 않는다. 열람 기록의 방식은 F2의 긴급 문의 원문 열람과 같다.
- **FR-020**: 번역본·원문을 포함한 어떤 정리 관련 응답에도 학부모의 이메일·연락처를 넣지 않는다.

**처리 단계**

- **FR-021**: 일반 문의의 처리 단계는 접수 → 정제 → 교사 확인 → 답변 완료이고, 이 기능은 "교사 확인"까지 단계를 쌓는다. "정제"는 검증을 통과한 정리 결과가 만들어졌을 때 기록한다. "원문 확인 필요"는 정제 완료가 아니다.
- **FR-022**: 일반 문의에는 "교사에게 전달됨" 단계를 두지 않는다(정제 완료가 교사에게 정리 결과가 보이는 시점이다). F2가 열어 둔 결정이다.
- **FR-023**: 단계 전이는 허용된 순서로만 하고, 같은 문의의 동시 변경은 한 번에 하나만 성공한다. 같은 문의의 정제 단계는 한 번만 기록된다.
- **FR-024**: 학부모는 본인 문의의 처리 단계를 시각과 함께 타임라인으로 본다. 정리 결과·정서강도·감정 라벨·실패 사유는 학부모에게 보이지 않는다.
- **FR-025**: 교사가 번역본을 처음 열람한 시점에 일반 문의의 처리 단계가 "교사 확인"으로 바뀌고 열람 시각이 단계 이력에 남는다. 두 번째 열람부터는 단계가 바뀌지 않는다. 번역본이 없는 "원문 확인 필요" 문의는 교사가 원문을 처음 열람한 시점에 "교사 확인"이 된다(접수 → 교사 확인). 번역본이 있는 문의는 원문을 열람해도 단계가 바뀌지 않는다.
- **FR-026**: 번역본 열람은 감사 기록 대상이 아니다(원칙 III는 원문 열람에 적용된다). 번역본의 첫 열람은 처리 단계 이력에만 남고, 원문 열람 기록(FR-019)과 별개다. **F5에서 변경(2026-10-28)**: 번역본 열람도 시도·완료·실패를 감사 기록에 남긴다(`INQUIRY_REFINEMENT_VIEW_*`). 기록이 실패해도 번역본은 반환하고 서버 로그(문의 ID·행위 종류·오류 종류)만 남긴다. 원문 열람 규칙은 그대로다 (`specs/006-audit-log-history` FR-003·005, research R3).

**권한·보안·로그**

- **FR-027**: 정리 결과(번역본)와 원문 열람은 담임 교사만 할 수 있다. 다른 학급 교사·다른 학부모·슈퍼 관리자는 거부된다. 거부는 존재 여부를 알리지 않는 방식이다(F2와 같음).
- **FR-028**: 문의 본문·가려진 본문·정리 결과·제목은 로그와 오류 응답에 남기지 않는다. 로그에는 식별자(UUID)와 상태만 남긴다.
- **FR-029**: 정리 결과는 원문처럼 암호화해 저장한다. 원문·정리 결과·처리 이력을 수정·삭제하는 기능은 제공하지 MUST NOT 한다(재시도는 새 결과를 덧붙이는 것이며 이전 기록을 고치지 않는다).
- **FR-030**: 외부 AI를 호출하는 키와 설정(모델)은 환경으로만 주입한다. 키나 모델 설정이 없거나 비어 있으면 서버는 기동을 거부한다(원칙 VIII). 실행 중의 외부 AI 장애는 FR-018대로 접수·긴급 경로에 영향을 주지 않는다.

**성능**

- **FR-031**: 접수부터 교사 화면에 번역본이 표시되기까지 평균 10초 이내를 목표로 한다.

**교사 알림 (F2 규칙 변경)**

- **FR-032**: 일반 문의의 교사 알림은 접수 즉시가 아니라 정리가 확정됐을 때 한 번 요청한다. 정리 확정은 검증을 통과한 번역본이 만들어진 때 또는 자동 재시도까지 실패해 "원문 확인 필요"가 확정된 때다. 정리 확정 전에는 일반 문의 알림을 요청하지 않는다. 알림은 고정 문구만 담는다(FR-014, F2).
- **FR-033**: F2의 일반 문의 알림 규칙(응답 가능 시간 밖이면 시작 때로 미룸, 일반 알림이 꺼져 있으면 보내지 않음, 쌓인 문의는 묶어 고정 문구 + 건수로 한 번만 알림)은 그대로 유지하되, "문의가 접수된 시각" 대신 "정리가 확정된 시각"을 기준으로 적용한다. 교사 재시도가 나중에 성공해도 같은 문의로는 추가 알림을 보내지 않는다.
- **FR-034**: 긴급 문의의 알림·재알림 규칙은 바뀌지 않는다. 긴급 알림은 접수 즉시 가고 정리나 위기 종류 분류를 기다리지 않는다.
- **FR-035**: F2에서 접수 즉시 만들어져 대기 중인 일반 문의 알림과 F3 이전에 접수된 일반 문의는 이관하지 않는다. 운영 배포 전이라 개발 데이터뿐이므로 F3 배포 전에 개발 DB를 비운다(팀 결정 2026-10-25, D5). F3 이후 접수되는 일반 문의는 접수 시점에 알림 요청을 만들지 않고 정리 확정 때 만든다.

**위기 종류 분류 (F2 연결 지점 채우기)**

- **FR-036**: 긴급 문의는 긴급 판정과 교사 전달이 끝난 뒤에, 가명화를 거친 글로 위기 종류를 자해 / 학대 / 그 밖의 안전 중 하나로 분류한다. 분류는 긴급 판정·교사 전달·알림 어느 것도 기다리게 하거나 바꾸지 않는다.
- **FR-037**: 분류도 외부 AI로 나가는 글이므로 FR-001~005의 가명화 규칙을 그대로 따른다. 가려지지 않은 원문은 분류에도 나가지 않는다.
- **FR-038**: 분류 결과는 정해진 값만 받고 서버가 허용값을 다시 검증한다. 허용된 값이 아니거나 분류가 실패·지연되면 "분류 안 됨"으로 보고, 학부모에게는 F2의 기본 안내(112·109 함께)가 그대로 보인다. 분류는 한 번만 시도하고 교사 재시도는 없다.
- **FR-039**: 분류 결과는 F2가 만든 연결 지점으로 넘기며, 학부모 안내는 F2의 규칙(자해 109, 학대 112, 그 밖의 안전 번호 없음)에 따라 고정 문구로만 보인다. 학부모 화면은 분류를 기다리지 않고 바로 뜨며, 분류가 늦게 끝나면 다시 열 때 종류에 맞는 안내로 바뀐다.
- **FR-040**: 분류 결과는 안내 문구를 고르는 데만 쓰고 긴급 표시·교사 전달·알림·권한 판단 같은 실행 경로에 쓰지 MUST NOT 한다. 한 번 정해진 분류 결과는 바뀌지 않는다.

### Key Entities *(include if feature involves data)*

- **정리 결과(번역본)**: 문의별 사실관계·요청사항·정서강도(3단계)·감정 라벨(최대 2개)·자동 생성 제목. 토큰은 정리 처리 중 메모리에서 원래 값으로 되돌린 뒤 원문처럼 암호화해 저장한다(대응표는 저장할 수 없으므로 나중에 되돌릴 수 없다, plan research R6). 덧붙이기만 하며 수정·삭제하지 않는다.
- **정리 시도 기록**: 문의별 정리 시도의 횟수·결과 상태(성공·검증 실패·응답 없음·가명화 실패)와 시각. 글 내용은 담지 않는다. 자동 재시도 1회와 교사 재시도 1회 한도를 판단하는 기준이다.
- **문의 정리 상태**: 정리 전(대기)·정리 완료·원문 확인 필요. 문의의 처리 단계(접수·정제·교사 확인)와 구분되는 표시이며, "원문 확인 필요"는 처리 단계를 앞으로 가게 하지 않는다.
- **가명화 대응표**: 토큰과 원래 값의 짝. 한 번의 정리 처리 동안만 메모리에 있고 어디에도 저장하지 않는다. 데이터로 남지 않는 개념이다.
- **원문 열람 기록(확장)**: F2의 열람 기록을 일반 문의에도 쓴다. 열람자(교사), 대상(문의), 시각이며 덧붙이기만 한다.
- **처리 단계 이력(확장)**: F2의 이력에 일반 문의의 "정제"와 "교사 확인" 단계를 더한다. 번역본의 첫 열람 시각이 "교사 확인"으로 남는다.
- **위기 종류 분류 결과**: 긴급 문의별 위기 종류(자해·학대·그 밖의 안전·분류 안 됨). 학부모 안내 문구를 고르는 데만 쓰이고 한 번 정해지면 바뀌지 않는다. F2의 연결 지점이 받는 값이다.
- **알림 요청(변경)**: 일반 문의의 알림 요청은 접수 시점이 아니라 정리 확정 시점에 만들어진다. 종류·지연·묶음 규칙은 F2와 같다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 외부 AI로 나간 글에서 학급 명단의 이름·학교·학급·전화번호·주소 패턴이 원래 값 그대로 발견되는 경우가 0건이다(대표 사례 모음 기준).
- **SC-002**: 토큰과 원래 값의 대응표가 저장소·로그·오류 응답 어디에서도 발견되지 않는다(0건).
- **SC-003**: 검증에 실패한 정리 결과가 교사에게 보이는 경우가 0건이다.
- **SC-004**: 정리 결과가 정상인 일반 문의는 접수부터 교사 화면의 번역본 표시까지 평균 10초 이내다.
- **SC-005**: 외부 AI가 완전히 중단되어도 접수·긴급 문의 전달·목록 표시·원문 열람은 100% 동작한다.
- **SC-006**: 자동 재시도와 교사 재시도를 합쳐 한 문의당 정리 시도가 3회를 넘는 경우가 0건이다.
- **SC-007**: 원문 열람마다 열람 기록이 남는 비율이 100%이고, 기록이 실패한 열람으로 원문이 나간 경우가 0건이다.
- **SC-008**: 다른 학급 교사·다른 학부모·슈퍼 관리자의 번역본·원문 접근 시도는 100% 거부된다.
- **SC-009**: 어떤 로그에서도 문의 본문·가려진 본문·정리 결과·제목이 발견되지 않는다.
- **SC-010**: 학부모에게 정리 결과·정서강도·감정 라벨이 노출되는 경우가 0건이다.
- **SC-011**: 정서강도 값이 3단계 밖이거나 감정 라벨이 고정 목록 밖·3개 이상인 결과가 교사에게 보이는 경우가 0건이다.
- **SC-012**: 같은 문의의 정제 단계와 "교사 확인" 단계가 두 번 이상 기록되는 경우가 0건이다.
- **SC-013**: 일반 문의 알림이 정리 확정 전에 나가는 경우가 0건이고, 정리가 확정된 문의의 알림은 100% 요청된다(응답 가능 시간·알림 설정 규칙에 따른 지연·차단은 제외).
- **SC-014**: 교사가 알림을 받고 연 일반 문의에서 번역본이나 "원문 확인 필요" 안내가 아닌 빈 화면이 보이는 경우가 0건이다.
- **SC-015**: 외부 AI가 완전히 중단되어도 긴급 문의의 알림·교사 전달·학부모 기본 안내가 100% 동작하고, 위기 종류 분류 때문에 지연되는 경우는 0건이다.
- **SC-016**: 위기 종류로 분류된 긴급 문의의 학부모 안내가 종류에 맞는 번호만 보이는 비율이 100%이고, 분류 안 됨·허용되지 않은 값일 때는 100% 기본 안내(112·109 함께)다.

## Assumptions

- 로그인·학부모–학생–담임 연결·학급 명단은 F1, 문의 접수·긴급 판정·원문 열람 기록·교사 알림 뼈대는 F2를 그대로 쓴다. 이 기능은 일반 문의의 정제를 채운다.
- 학급 명단 사전은 접수 시점의 문의 학급(학생·보호자·교사 이름)과 학교·학급 정보에서 만든다. 명단에 없는 사람 이름은 사전으로는 찾지 못하며, 1차·2차 치환으로 가려지지 않는 정보가 외부로 나갈 수 있다는 한계를 plan에서 명시하고 대표 사례로 점검한다.
- 외부 AI 호출은 가명화를 거친 글만 받는 하나의 경로로 만든다(원칙 II). 어떤 외부 AI를 쓰는지와 호출 방식은 plan에서 정한다.
- 되묻기(AI가 학부모에게 추가 질문)는 MVP 범위 밖이다(팀 결정 2026-10-15).
- 정서강도 3단계와 감정 라벨 목록(불안·불만·분노·걱정·답답함·슬픔, 최대 2개)은 팀 결정으로 고정한다. 목록 변경은 PR 리뷰와 배포를 거친다.
- 정서강도·감정 라벨은 교사의 참고 표시일 뿐이고 긴급 판정을 바꾸지 않는다. 일반 문의가 긴급으로 바뀌는 경로는 F2의 규칙뿐이다.
- 이 기능은 F2가 이미 구현한 동작 두 가지를 바꾼다: ① 일반 문의 알림이 접수 즉시가 아니라 정리 확정 시점에 가는 것(FR-032~035), ② F2가 비워 둔 위기 종류 분류 연결 지점을 채우는 것(FR-036~040). F2 spec(`specs/002-inquiry-intake-urgent`)의 해당 요구사항(FR-027·028·030, SC-007 중 일반 문의 알림 시점)과 F2 코드는 plan·tasks 단계에서 함께 고친다. 긴급 문의 동작은 바꾸지 않는다.
- 일반 문의에 "교사에게 전달됨" 단계는 두지 않는다. F2가 F3에서 정하기로 한 사항이며, 정제 완료가 교사에게 정리 결과가 보이는 시점이다.
- 자동 재시도는 1회, 교사 재시도는 문의 1건당 1회다. 그 이후에는 원문 확인만 가능하다(팀 결정).
- F3 이전에 접수되어 "접수"에 머물러 있는 일반 문의는 정리 대상에 넣지 않는다. 개발 데이터뿐이므로 F3 배포 전에 개발 DB를 비운다(FR-035, 팀 결정 2026-10-25 D5).
- 학부모에게 보이는 문구는 모두 사전 정의된 고정 문구이고 AI가 만든 문장을 학부모에게 보내지 않는다(원칙 V). 정리 결과는 교사에게만 보인다.
- 교사에게 가는 알림은 고정 문구만 쓰고 본문·이름을 담지 않는다. 알림 수단은 F2가 만든 것을 쓴다.
- 파일 첨부, 되묻기, 답변 작성·점검·전송(F4), 감사 로그 조회(F5)는 이 기능의 범위 밖이다.
